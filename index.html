React od zera — teoria

Ten kurs przygotowuje Cię do Części II arkusza INF.04 — aplikacji webowej wykonywanej w React.js. Jeśli miałeś/aś już INF.03, znasz PHP, HTML, CSS i podstawy JavaScriptu — to solidny fundament, na którym tu budujemy. React jest jednak inny w podejściu: nie mówisz przeglądarce „zmień ten element”, tylko opisujesz, jak ma wyglądać interfejs dla aktualnych danych, a React sam dba o resztę.

Każda lekcja tłumaczy jeden mechanizm na małym, samodzielnym przykładzie — liczbach, osobach, produktach, zadaniach — celowo nie na danych z konkretnego arkusza. Na egzaminie dostaniesz własne, nieznane wcześniej zadanie, więc chodzi o to, żebyś zrozumiał/a sam mechanizm, a nie zapamiętał/a jedno rozwiązanie. Po przerobieniu kursu powinieneś/aś samodzielnie umieć zastosować go do dowolnego zadania: wyświetlić zestaw danych na ekranie i obsłużyć interakcje użytkownika, takie jak kliknięcia, zaznaczanie pól czy wypełnianie formularza.

Lekcja 1 · Część A

Czym jest React i po co go używać

React to biblioteka JavaScript (nie pełny framework, choć w praktyce często pełni tę rolę) do budowania interfejsów użytkownika, stworzona przez Facebooka/Metę. Rozwiązuje konkretny problem, który już znasz z innej strony.

W PHP renderowanie dzieje się po stronie serwera: przeglądarka wysyła żądanie, serwer generuje gotowy HTML i go odsyła. W „czystym” JavaScript + DOM ręcznie manipulujesz stroną: document.getElementById(...).innerText = ..., dopisujesz elementy, usuwasz klasy. Przy prostym interfejsie to działa, ale przy interfejsie, w którym jedna akcja użytkownika zmienia kilka miejsc na ekranie naraz, ręczne śledzenie „co się zmieniło i gdzie to zaktualizować” szybko robi się chaotyczne.

React proponuje podejście deklaratywne: piszesz funkcję, która na podstawie aktualnych danych (stanu) zwraca opis tego, jak ma wyglądać interfejs. Gdy dane się zmieniają, każesz Reactowi przeliczyć ten opis od nowa — a on sam ustala, które fragmenty prawdziwej strony trzeba faktycznie zaktualizować.

Aplikacja React to drzewo komponentów — samodzielnych, wielokrotnego użytku fragmentów UI zapisanych jako funkcje.

Sprawdź się

Jednym zdaniem: czym różni się sposób, w jaki PHP generuje stronę, od sposobu, w jaki React aktualizuje stronę po zmianie danych?

Pokaż przykładową odpowiedź

PHP generuje cały HTML na serwerze przy każdym żądaniu strony; React działa już w przeglądarce i po zmianie danych (stanu) sam przelicza, który fragment już wyrenderowanej strony trzeba zaktualizować, bez przeładowania całej strony.

Lekcja 2 · Część A

Node.js i npm

Node.js to środowisko uruchomieniowe JavaScript poza przeglądarką (zbudowane na silniku V8 z Chrome). Dzięki niemu JS może działać jak zwykły program w terminalu — np. serwer budujący i podający Twoją aplikację podczas pracy nad nią.

npm (Node Package Manager) to menedżer pakietów dla JavaScriptu — odpowiednik Composera w PHP. Plik package.json w projekcie opisuje: jakich bibliotek używa projekt (dependencies), oraz jakie polecenia można uruchomić (scripts, stąd npm run dev).

npm install pobiera wszystkie zależności do folderu node_modules — potrafi mieć dziesiątki tysięcy plików. Ten folder nigdy nie jest częścią kodu źródłowego, który się przegląda czy przenosi — jest odtwarzalny w każdej chwili z package.json poleceniem npm install.

Otwórz plik package.json w dowolnym projekcie React i znajdź sekcję "dependencies". Jakie pakiety tam widzisz i domyślasz się, do czego służą?

Pokaż przykładową odpowiedź

Powinny tam być co najmniej react i react-dom — pierwsza to sama biblioteka Reacta, druga to warstwa łącząca React z prawdziwym DOM przeglądarki.

Lekcja 3 · Część A

Vite — narzędzie budujące

Kod, który piszesz w React (JSX, nowoczesna składnia JS) nie jest zrozumiały bezpośrednio dla przeglądarki. Potrzebny jest proces budowania (build), który: (1) tłumaczy (transpiluje) JSX i nowoczesny JS na zwykły JavaScript zrozumiały dla przeglądarek, (2) łączy wiele plików w mniejszą liczbę pakietów (bundling), (3) w trybie deweloperskim serwuje aplikację z automatycznym odświeżaniem po każdej zmianie w kodzie (tzw. Hot Module Replacement) — dlatego zapisana zmiana w kodzie pojawia się w przeglądarce niemal natychmiast, bez ręcznego odświeżania.

Vite (czyt. „wit”, od francuskiego „szybko”) to nowoczesne, bardzo szybkie narzędzie tego typu — następca starszych rozwiązań jak Webpack czy Create React App.

Polecenia, które warto znać na pamięć

Na egzaminie projekt zakładasz od zera, bez ściągi — te cztery polecenia warto umieć bez zastanowienia. Wpisujesz je w terminalu, w folderze, w którym ma powstać projekt:

# 1. utworzenie projektu o nazwie "egzamin" z szablonu React (wariant JavaScript)
npm create vite@latest egzamin -- --template react

# 2. wejście do folderu projektu
cd egzamin

# 3. pobranie zależności (React, Vite) do node_modules
npm install

# 4. uruchomienie serwera deweloperskiego — adres pojawi się w terminalu
npm run dev

Kreator może zadać dodatkowe pytania (np. o linter) — dla zadania egzaminacyjnego nie mają znaczenia, wybierz domyślne opcje. Serwer zatrzymasz w terminalu skrótem Ctrl+C. Jeśli npm zostanie zablokowany przez PowerShell, rozwiązanie znajdziesz w Lekcji 27.

Sprawdź się

Przy działającym npm run dev zmień dowolny widoczny tekst w komponencie i zapisz plik. Ile czasu minęło, zanim zmiana pojawiła się w przeglądarce — i czy musiałeś/aś ręcznie ją odświeżyć?

Pokaż przykładową odpowiedź

Zmiana powinna pojawić się niemal natychmiast (ułamek sekundy), bez ręcznego odświeżania — to właśnie Hot Module Replacement w akcji.

Lekcja 4 · Część A

Struktura projektu Vite + React

Zobaczmy dokładnie, co Vite wygenerował, plik po pliku — z prawdziwą zawartością i wyjaśnieniem każdej linijki, którą warto rozumieć.

egzamin/
├── index.html          ← jedyny plik HTML w całym projekcie
├── package.json         ← lista zależności i poleceń (Lekcja 2)
├── vite.config.js       ← konfiguracja narzędzia budującego (Lekcja 3)
├── public/               ← pliki statyczne, serwowane bez zmian
│   └── assets/            ← tu trafiają np. zdjęcia z zadania
├── src/                  ← tu piszesz cały właściwy kod
│   ├── main.jsx            ← punkt wejścia
│   ├── App.jsx              ← główny komponent
│   ├── App.css              ← style "dla App"
│   └── index.css            ← style globalne
└── node_modules/          ← zainstalowane paczki (Lekcja 2), nie ruszamy

index.html

Jedyny prawdziwy plik HTML w projekcie — cała reszta aplikacji powstaje już w JavaScripcie. Prawdziwa zawartość wygenerowana przez Vite:

<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <link rel="icon" type="image/svg+xml" href="/favicon.svg" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>egzamin</title>
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.jsx"></script>
  </body>
</html>

Trzy rzeczy warte zauważenia:

  • <title>egzamin</title> — tytuł karty przeglądarki. To zwykły, nazwany tak, jak folder Twojego projektu (możesz go zmienić na cokolwiek).
  • <div id="root"></div> — pusty div. To jedyny fragment strony, który React kiedykolwiek zobaczy i wypełni swoją treścią. Wszystko, co dotąd wyrenderowałeś/aś (nagłówki, zdjęcia, przyciski), fizycznie ląduje w środku tego jednego diva.
  • <script type="module" src="/src/main.jsx"></script> — ładuje Twój kod JavaScript. type="module" mówi przeglądarce, że to nowoczesny moduł JS (obsługujący import/export z Lekcji 12), a nie zwykły, staroświecki skrypt.

src/main.jsx

Prawdziwa zawartość wygenerowana przez Vite:

import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import './index.css'
import App from './App.jsx'

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>,
)

Linijka po linijce:

  • import { StrictMode } from 'react' i import { createRoot } from 'react-dom/client' — importy nazwane (Lekcja 12) z paczek Reacta.
  • import './index.css' — import pliku CSS bezpośrednio w JS. To specjalna sztuczka, którą rozumie Vite (zwykły JavaScript w przeglądarce tego nie potrafi) — w efekcie te style trafiają na całą stronę.
  • import App from './App.jsx' — import domyślny Twojego komponentu (Lekcja 12), stąd brak klamer.
  • document.getElementById('root') — znajduje w prawdziwym DOM ten sam <div id="root">, który widziałeś/aś w index.html.
  • createRoot(...).render(<App />) — tworzy „korzeń” aplikacji React w tym divie i każe wyrenderować w nim komponent App. Od tego momentu React przejmuje kontrolę nad wszystkim wewnątrz tego diva.
  • <StrictMode>...</StrictMode> — opcjonalny „tryb czujności” Reacta, wyłącznie na czas developmentu. Nie renderuje niczego widocznego na ekranie — celowo wywołuje niektóre funkcje dwukrotnie, żeby łatwiej wychwycić błędy (np. przypadkowe mutacje, o których uczysz się w Lekcji 22). W finalnej, zbudowanej aplikacji (npm run build) nie ma żadnego wpływu na działanie. Możesz go spokojnie zostawić bez ruszania.

Tego pliku praktycznie nigdy nie edytujesz w projekcie na egzamin — cała Twoja praca dzieje się w App.jsx.

src/App.css i src/index.css — ważna nieoczywistość

Oba pliki to zwykłe, globalne arkusze CSS — mimo nazwy App.css, nic w tym pliku nie jest automatycznie „zamknięte” wyłącznie w komponencie App. To tylko konwencja nazewnicza („style, które koncepcyjnie należą do App”), a nie mechanizm techniczny — selektor napisany w App.css zadziała tak samo, jakby był w index.css. Różnica jest wyłącznie organizacyjna: index.css zwykle trzyma naprawdę globalne rzeczy (reset stylów, czcionka bazowa), a plik komponentu — style tego, co ten komponent renderuje. W Twoim projekcie na egzamin możesz spokojnie trzymać wszystkie własne style w jednym z tych plików (albo w obu, jeśli wolisz je rozdzielić) — obie ścieżki są poprawne.

package.json — bliżej

Poznałeś/aś już ten plik pobieżnie w Lekcji 2. Realna zawartość Twojego projektu:

{
  "name": "egzamin",
  "private": true,
  "type": "module",
  "scripts": {
    "dev": "vite",
    "build": "vite build",
    "lint": "eslint .",
    "preview": "vite preview"
  },
  "dependencies": {
    "react": "^19.2.8",
    "react-dom": "^19.2.8"
  },
  "devDependencies": {
    "vite": "^8.2.2"
    // (i kilka innych, pominiętych tu dla czytelności)
  }
}
  • "scripts" — nazwane skróty na polecenia terminala. npm run dev uruchamia to, co jest wpisane pod "dev" (czyli po prostu vite) — stąd ta konkretna nazwa polecenia, którą wpisujesz.
  • "dependencies" — paczki potrzebne, żeby aplikacja działała (React sam w sobie).
  • "devDependencies" — paczki potrzebne wyłącznie Tobie, w trakcie pisania kodu (Vite, linter) — nie są częścią tego, co ostatecznie trafia do przeglądarki użytkownika po zbudowaniu aplikacji.

public/ kontra src/assets/ — przypomnienie

Pliki w public/ są serwowane bez żadnego przetwarzania, pod ścieżką liczoną od korzenia strony (public/assets/obraz1.jpg → w kodzie /assets/obraz1.jpg), więc nie trzeba ich importować jako moduły JS — wystarczy zwykły string ze ścieżką. Pliki w src/assets/ musiałyby być importowane pojedynczo jako moduły, co przy dynamicznych nazwach plików pochodzących z danych (a nie wpisanych na sztywno w kodzie) jest niewygodne. Dlatego przy zadaniu z galerią zdjęć, gdzie nazwa pliku pochodzi z tablicy danych, wygodniejszym wyborem jest public/assets.

Część B

Niezbędne podstawy JavaScript (ES6+)

React intensywnie korzysta z nowoczesnej składni JS. Zanim wrócimy do samego Reacta, upewnijmy się, że ta składnia nie będzie Cię zaskakiwać.

Lekcja 5 · Część B

const i let

Starsze var warto dziś pomijać — ma nieintuicyjne zasady zasięgu. Zamiast tego: let dla zmiennej, której wartość faktycznie się zmieni, const dla stałej.

Uwaga na częste nieporozumienie: const oznacza, że nie możesz przypisać zmiennej zupełnie nowej wartości (lista = [] po deklaracji przez const da błąd), ale jeśli wartością jest obiekt albo tablica, możesz swobodnie zmieniać jego zawartość (tablica.push(x) nie jest błędem składniowym) — to sama referencja do wartości jest „zablokowana”, nie jej wnętrze. W Reakcie i tak prawie nigdy nie zmienia się zawartości w miejscu (o tym w Lekcji 22), więc w praktyce niemal wszystko deklarujesz przez const.

Sprawdź się

Mając const lista = [1, 2], wyjaśnij: dlaczego lista.push(3) zadziała bez błędu, a lista = [4, 5] zgłosi błąd?

Pokaż przykładową odpowiedź

const blokuje wyłącznie przypisanie nowej wartości do samej zmiennej lista — a lista = [4, 5] właśnie to próbuje zrobić. lista.push(3) nie zmienia tego, na co wskazuje zmienna lista (to dalej ta sama tablica w pamięci) — zmienia tylko jej zawartość w miejscu, co const w ogóle nie blokuje.

Lekcja 6 · Część B

Funkcje strzałkowe

Krótszy zapis funkcji, używany w Reakcie niemal wszędzie — w obsłudze zdarzeń, w .map()/.filter(), w hookach. Warto poznać ją naprawdę dobrze, bo pojawia się dosłownie w każdym pliku .jsx.

function podwoj(x) {
  return x * 2
}

// to samo jako funkcja strzałkowa:
const podwoj = (x) => x * 2

Warianty zapisu

Zapis funkcji strzałkowej zmienia się w zależności od liczby argumentów i długości ciała funkcji. Wszystkie poniższe formy są poprawne i będziesz je spotykać zamiennie:

// zero argumentów — nawiasy obowiązkowe, nawet puste
const przywitaj = () => "Cześć!"

// jeden argument — nawiasy opcjonalne (obie formy poprawne)
const podwoj = x => x * 2
const podwoj2 = (x) => x * 2

// kilka argumentów — nawiasy obowiązkowe
const dodaj = (a, b) => a + b

// pojedyncze wyrażenie — "niejawny" return (wynik wyrażenia jest zwracany automatycznie)
const kwadrat = (x) => x * x

// kilka instrukcji — klamry + jawne "return" (bez return funkcja zwróci undefined)
const opisz = (osoba) => {
  const dorosly = osoba.wiek >= 18
  return osoba.imie + (dorosly ? " jest dorosła" : " jest niepełnoletnia")
}

Praktyczna rada: gdy masz tylko jeden argument, obie formy (x => ... i (x) => ...) są równie poprawne — trzymaj się jednej konwencji w całym projekcie (w tym kursie używamy nawiasów zawsze, dla spójności z wersją wieloargumentową).

Pułapka: zwracanie obiektu wprost

Przy niejawnym return (bez klamer) chcesz czasem zwrócić od razu obiekt. Problem: JavaScript widzi klamrę { zaraz po strzałce i myśli, że to początek bloku kodu (jak przy jawnym return), a nie obiekt:

// BŁĄD: JS próbuje to odczytać jako blok kodu z etykietą "imie", nie jako obiekt
const stworzOsobe = (imie, wiek) => { imie: imie, wiek: wiek }

// OK: dodatkowe nawiasy okrągłe jednoznacznie mówią "to jest wyrażenie (obiekt), nie blok"
const stworzOsobe = (imie, wiek) => ({ imie: imie, wiek: wiek })

To bardzo częsty, mylący błąd u początkujących — funkcja z pierwszego przykładu nie wyrzuci nawet czerwonego błędu, tylko po prostu zwróci undefined, co bywa trudne do wyśledzenia. Zasada: jeśli niejawnie zwracasz obiekt, zawsze owijaj go w nawiasy okrągłe.

Funkcje strzałkowe jako argumenty

Najczęstsze zastosowanie w praktyce: funkcja strzałkowa przekazana jako argument do innej funkcji (tzw. callback) — dokładnie tak, jak w .map() i .filter() z Lekcji 8:

const liczby = [4, 9, 15, 22]

// funkcja strzałkowa zdefiniowana "w locie", od razu jako argument .filter()
const parzyste = liczby.filter((n) => n % 2 === 0)  // [4, 22]

Nie musisz najpierw nazywać funkcji osobną stałą — możesz ją zdefiniować bezpośrednio w miejscu, gdzie jest potrzebna. To właśnie robi ją tak wygodną w połączeniu z .map(), .filter() i obsługą zdarzeń w JSX.

Pułapka: wywołanie natychmiastowe zamiast opóźnionego

Najważniejsza pułapka, na którą natkniesz się przy obsłudze przycisków: onClick={usun(id)} wywoła usun natychmiast, w trakcie renderowania komponentu — nie przy kliknięciu! Żeby funkcja wykonała się dopiero po kliknięciu, trzeba przekazać samą funkcję strzałkową, która dopiero w środku wywoła usun:

// BŁĄD: usun(id) wykonuje się od razu przy renderowaniu, nie przy kliknięciu
<button onClick={usun(id)}>Usuń</button>

// OK: onClick dostaje funkcję, która wywoła usun(id) dopiero po kliknięciu
<button onClick={() => usun(id)}>Usuń</button>

Ten sam wzorzec przydaje się, gdy przy jednym kliknięciu trzeba wykonać kilka rzeczy naraz — wtedy funkcja strzałkowa dostaje ciało z klamrami (bez return, bo onClick nie oczekuje żadnej zwracanej wartości):

<button onClick={() => {
  console.log("Kliknięto element o id " + id)
  usun(id)
}}>
  Usuń
</button>

Przypomnienie: dostęp do elementu tablicy przez indeks

Zanim połączymy obiekty z tablicami, krótkie przypomnienie samego indeksowania tablic — przydatne teraz, i jeszcze bardziej za chwilę. Każdy element tablicy ma swoją pozycję, liczoną od zera, dostępną w nawiasach kwadratowych:

const owoce = ["jabłko", "gruszka", "śliwka"]

owoce[0]  // "jabłko" — pierwszy element
owoce[1]  // "gruszka" — drugi element
owoce[2]  // "śliwka" — trzeci element

Stąd właśnie liczenie „od zera” — indeks to nie numer porządkowy (1., 2., 3.), tylko przesunięcie od początku tablicy (0 kroków, 1 krok, 2 kroki).

Tablica obiektów

Skoro elementem tablicy może być cokolwiek, w tym obiekt, można połączyć oba mechanizmy — to dokładnie kształt danych, z jakim najczęściej pracuje się w React (i dokładnie kształt dane.txt z arkusza egzaminacyjnego):

const produkty = [
  { nazwa: "Zeszyt", cena: 4.5 },
  { nazwa: "Długopis", cena: 2.2 },
  { nazwa: "Linijka", cena: 1.8 },
]

Żeby dostać się do konkretnego pola konkretnego obiektu, łączysz oba poznane mechanizmy — najpierw indeks (który obiekt), potem kropka (które pole):

produkty[0].nazwa   // "Zeszyt" — pole "nazwa" pierwszego obiektu
produkty[1].cena    // 2.2 — pole "cena" drugiego obiektu

To wciąż „długa droga” — działa tylko wtedy, gdy z góry znasz dokładny indeks. Żeby zrobić to samo dla każdego obiektu w tablicy naraz (np. wyświetlić wszystkie produkty na ekranie), zamiast ręcznie powtarzać produkty[0], produkty[1], produkty[2]..., poznasz w następnej lekcji dużo wygodniejszy sposób: metodę .map().

Lekcja 8 · Część B

Tablice i metody .map(), .filter()

.map(funkcja) przechodzi przez każdy element tablicy, wywołuje na nim funkcję i zwraca nową tablicę tej samej długości, złożoną z wyników. .filter(funkcja) przechodzi przez każdy element, a funkcja decyduje (zwracając true/false), czy dany element ma się znaleźć w nowej, krótszej (albo takiej samej) tablicy wynikowej. To dwie z najczęściej używanych metod w całym Reakcie, więc warto poznać je naprawdę dokładnie — łącznie z pułapkami, w które regularnie wpadają początkujący.

.map() — analogia i krok po kroku

Wyobraź sobie kowala w grze RPG: przynosisz mu cały ekwipunek do naostrzenia. Każdy przedmiot dostaje to samo ulepszenie (+1 do obrażeń), a Ty wracasz z plecaka — dokładnie z taką samą liczbą przedmiotów, co przyniosłeś, tylko każdy mocniejszy. Tak właśnie działa .map(): dla każdego elementu wejściowego dostajesz dokładnie jeden element wyjściowy, przetworzony tą samą funkcją.

const liczby = [3, 8, 15]
const podwojone = liczby.map((n) => n * 2)

// co dzieje się krok po kroku:
// n = 3  -> funkcja zwraca 6
// n = 8  -> funkcja zwraca 16
// n = 15 -> funkcja zwraca 30
// podwojone === [6, 16, 30]  — trzy elementy weszły, trzy wyszły

.map() na tablicy obiektów

W praktyce (i w Reakcie) dużo częściej mapujesz tablice obiektów niż pojedynczych liczb — np. żeby wyciągnąć z każdego obiektu jedno pole, albo zbudować z niego coś nowego:

const uczniowie = [
  { imie: "Ala", ocena: 5 },
  { imie: "Bartek", ocena: 3 },
]

// wyciągnięcie samych imion — tablica stringów
const imiona = uczniowie.map((u) => u.imie)  // ["Ala", "Bartek"]

// zbudowanie nowych obiektów na podstawie starych
const opisy = uczniowie.map((u) => u.imie + ": " + u.ocena)
// ["Ala: 5", "Bartek: 3"]

To dokładnie ten sam wzorzec, który w Lekcji 17 zamieni tablicę danych na tablicę elementów JSX — .map() nie „wie” i nie musi wiedzieć, czy to co zwraca to liczba, tekst, obiekt czy kawałek interfejsu.

Pułapka: zapomniany return

To zdecydowanie najczęstszy błąd z .map() u początkujących — połączenie z pułapką z Lekcji 6 (ciało wieloliniowe wymaga jawnego return):

// BŁĄD: ciało z klamrami, ale bez return
const podwojone = liczby.map((n) => {
  n * 2
})
// podwojone === [undefined, undefined, undefined]
// funkcja faktycznie policzyła n * 2 dla każdego elementu, ale nic nie zwróciła!

Kod się nie wywala, nie ma żadnego czerwonego błędu — po prostu dostajesz tablicę samych undefined, tej samej długości co oryginał. To bywa mylące, bo wygląda na to, że „coś działa” (długość się zgadza), a naprawdę nic sensownego się nie wydarzyło. Zasada: jeśli używasz klamer { } w funkcji przekazanej do .map(), zawsze sprawdź, czy jest w niej return.

Pułapka: wynik trzeba przechować

.map() (podobnie jak .filter()) nie zmienia oryginalnej tablicy — zwraca zupełnie nową. Jeśli wywołasz go i nie zapiszesz wyniku, efekt przepada:

// BŁĄD: wynik .map() nigdzie nie trafia, ginie
liczby.map((n) => n * 2)
console.log(liczby)  // dalej [3, 8, 15] — bez zmian!

// OK: wynik zapisany do nowej stałej
const podwojone = liczby.map((n) => n * 2)
console.log(podwojone)  // [6, 16, 30]

Jeśli chcesz tylko wykonać coś dla każdego elementu (np. console.log) i nie potrzebujesz nowej tablicy jako wyniku, właściwym narzędziem jest .forEach() z Dodatku, nie .map().

.filter() — analogia i przykład

Znasz pewnie filtr ekwipunku z gier RPG (Diablo, Path of Exile, WoW) — włączasz np. "pokaż tylko legendarne" i z całego plecaka, pełnego różnych przedmiotów, widzisz tylko te spełniające warunek, reszta się chowa z widoku, ale fizycznie dalej jest w plecaku. Dokładnie tak działa .filter(): dla każdego elementu sprawdza jeden warunek (funkcję, którą sam definiujesz — nie musi to być rzadkość przedmiotu, może być cokolwiek), i do nowej, wynikowej tablicy przepuszcza tylko te, dla których warunek dał true, w tej samej kolejności, w jakiej były w oryginale.

const liczby = [3, 8, 15, 42, 4]
const duze = liczby.filter((n) => n > 10)

// co dzieje się krok po kroku:
// n = 3  -> 3 > 10 to false  -> odrzucone
// n = 8  -> 8 > 10 to false  -> odrzucone
// n = 15 -> 15 > 10 to true  -> zostaje
// n = 42 -> 42 > 10 to true  -> zostaje
// n = 4  -> 4 > 10 to false  -> odrzucone
// duze === [15, 42]

W przeciwieństwie do .map(), wynikowa tablica nie musi mieć tej samej długości co wejściowa — może mieć mniej elementów albo (jeśli wszystkie przejdą warunek) tyle samo. Może też wyjść pusta tablica [], jeśli nic nie spełnia warunku — to nie błąd, tylko normalny, poprawny wynik, który trzeba umieć obsłużyć (np. wyświetlić „Brak wyników” zamiast pustej listy).

Pułapka: zapomniany return w .filter()

Ten sam błąd co w .map(), ale ze zwodniczo innym skutkiem — undefined jest wartością „falsy” (Lekcja 11), więc funkcja bez return zachowuje się tak, jakby zawsze zwracała false:

// BŁĄD: brak return w ciele z klamrami
const duze = liczby.filter((n) => {
  n > 10
})
// duze === [] — pusta tablica, mimo że 15 i 42 spełniają warunek!

To szczególnie podstępny wariant tego błędu: kod nie wywala się, nie ma czerwonego napisu — po prostu .filter() po cichu odrzuca wszystko, bo „brak zwróconej wartości” jest traktowany jak „warunek niespełniony”.

Pułapka: = zamiast ===

Jeden znak różnicy, zupełnie inne działanie — pojedynczy = to przypisanie (nadanie nowej wartości), nie porównanie:

// BŁĄD: to przypisanie (n = 10), nie porównanie!
const wynik = liczby.filter((n) => n = 10)

// OK: porównanie ścisłe (Lekcja 11)
const wynik2 = liczby.filter((n) => n === 10)

Pierwsza wersja w wielu przypadkach da błąd składniowy albo nieoczekiwany wynik (bo wyrażenie przypisania samo w sobie ma wartość — tę przypisaną). To kolejny dobry powód, żeby zawsze pisać ===/== świadomie i nigdy nie „zgadywać” liczby znaków równości.

Łączenie .filter() i .map() w łańcuch

Bardzo częsty, praktyczny wzorzec: najpierw zawęź dane (.filter()), potem przekształć to, co zostało (.map()). Skoro obie metody zwracają tablicę, można je łączyć jedna po drugiej — dokładnie tak, jak w Module 4 Twojego projektu (najpierw filtrowanie po kategorii, potem renderowanie):

const uczniowie = [
  { imie: "Ala", ocena: 5 },
  { imie: "Bartek", ocena: 3 },
  { imie: "Celina", ocena: 5 },
]

const imionaNajlepszych = uczniowie
  .filter((u) => u.ocena === 5)   // zostają Ala i Celina
  .map((u) => u.imie)             // ["Ala", "Celina"]

Kolejność ma znaczenie dla czytelności i wydajności: filtrowanie najpierw oznacza, że .map() przetwarza już tylko te elementy, które naprawdę są potrzebne, zamiast przekształcać wszystko, a dopiero potem coś odrzucać.

Lekcja 9 · Część B

Destrukturyzacja

Destrukturyzacja nie robi nic nowego — to wyłącznie krótszy zapis czegoś, co już potrafisz zrobić. Zobaczmy najpierw „długą drogę”, a potem skrót.

Z tablicy

Znasz już indeksowanie tablic z Lekcji 7. Żeby wyciągnąć z tablicy dwie wartości do osobnych zmiennych, napisałbyś/abyś:

const dane = [10, 20]

const pierwszy = dane[0]
const drugi = dane[1]

Destrukturyzacja tablicowa robi dokładnie to samo, w jednej linijce:

const [pierwszy, drugi] = dane
// dokładnie to samo, co dwie linijki wyżej: pierwszy = 10, drugi = 20

Liczy się tu wyłącznie pozycja — pierwszy zawsze dostaje element o indeksie 0, drugi element o indeksie 1, niezależnie od tego, jak nazwiesz same zmienne. Mógłbyś/abyś równie dobrze napisać const [a, b] = dane i dostałbyś/abyś te same wartości pod innymi nazwami.

Z obiektu

Analogicznie z obiektem — znasz już dostęp przez kropkę z Lekcji 7:

const osoba = { imie: "Ala", wiek: 17 }

const imie = osoba.imie
const wiek = osoba.wiek

Skrót — destrukturyzacja obiektowa:

const { imie, wiek } = osoba
// dokładnie to samo, co dwie linijki wyżej

Tu jednak jest ważna różnica względem tablicy: nazwy w klamrach muszą zgadzać się z rzeczywistymi nazwami pól w obiekcie (bo tak JavaScript wie, którego pola szukać) — nie możesz dowolnie ich zmienić, tak jak przy tablicy. Liczy się nazwa, nie pozycja pola w obiekcie.

Mała zapowiedź na później

Pełne wyjaśnienie dopiero w Lekcji 20, na razie potraktuj to jako czystą ciekawostkę o samej składni: w React bardzo często zobaczysz taki zapis:

const [wartosc, setWartosc] = useState(0)

useState(...) to specjalna funkcja Reacta, która zawsze zwraca parę: aktualną wartość i funkcję do jej zmiany, zapakowane w dwuelementową tablicę — dlatego po lewej stronie widzisz dokładnie tę samą destrukturyzację tablicową, którą właśnie poznałeś/aś, tylko zastosowaną nie do zwykłej tablicy zapisanej wprost (jak [10, 20]), a do tablicy zwróconej przez funkcję. Mechanizm jest identyczny. Nie musisz teraz rozumieć, co ta funkcja robi ani dlaczego React jej używa — to temat na osobną, dużą lekcję. Chodzi wyłącznie o to, żebyś rozpoznał/a ten zapis jako „zwykłą” destrukturyzację tablicową, gdy go zobaczysz.

Lekcja 10 · Część B

Operator rozproszenia — spread (...)

... (spread) „rozwija” zawartość tablicy lub obiektu w nowe miejsce. Podobnie jak destrukturyzacja z poprzedniej lekcji, to skrót na coś, co dałoby się (niewygodnie) zrobić ręcznie — zobaczmy najpierw długą drogę.

Obiekty — długa droga i skrót

Masz obiekt i chcesz stworzyć jego kopię z jednym zmienionym polem, nie ruszając oryginału (dlaczego to takie ważne w Reakcie, wyjaśnia Lekcja 22 — na razie skup się na samej mechanice). Bez żadnej nowej składni musiałbyś/abyś ręcznie przepisać każde pole osobno, zmieniając tylko to jedno:

const produkt = { id: 5, nazwa: "Zeszyt", cena: 4.5 }

// długa droga: ręcznie przepisujesz WSZYSTKIE pola, jedno zmieniając
const przeceniony = {
  id: produkt.id,
  nazwa: produkt.nazwa,
  cena: 3,
}

Działa, ale przy obiekcie z dziesięcioma polami musiałbyś/abyś przepisać wszystkie dziesięć, żeby zmienić jedno. Spread robi dokładnie to samo w jednej linijce:

const przeceniony = { ...produkt, cena: 3 }
// { id: 5, nazwa: "Zeszyt", cena: 3 } — dokładnie ten sam wynik, co wyżej

...produkt oznacza „skopiuj tu wszystkie pola z produkt”, a to, co napiszesz po nim, nadpisuje wybrane pole nową wartością.

Pułapka: kolejność ma znaczenie

Spread działa jak zwykłe przepisywanie pól odgórnie w dół — to, co jest napisane później, nadpisuje to, co wcześniej. Jeśli przez pomyłkę umieścisz spread na końcu, cofnie on Twoją zmianę:

// BŁĄD: spread na końcu nadpisuje cenę z powrotem na oryginalną wartość!
const przeceniony = { cena: 3, ...produkt }
// { id: 5, nazwa: "Zeszyt", cena: 4.5 } — cena wróciła do 4.5, nie tego chcieliśmy

Zasada: spread zawsze na początku (kopiujesz wszystko), a nadpisywane pola po nim (żeby wygrały z tym, co skopiowane).

Tablice — spread kontra .push()

Ten sam operator działa też na tablicach — i tu jest kluczowy powód, dla którego wolimy go od już znanej Ci z Dodatku metody .push():

const tablica = [1, 2, 3]

// .push() MUTUJE oryginalną tablicę — zmienia ją w miejscu
tablica.push(4)
// tablica === [1, 2, 3, 4] — ta sama tablica w pamięci, tylko zmieniona

// spread NIE mutuje — tworzy zupełnie nową tablicę
const rozszerzona = [...tablica, 4]
// tablica zostaje bez zmian, rozszerzona to nowa, osobna tablica z dodatkowym elementem

W Reakcie prawie zawsze chcesz drugiego wariantu — nowej tablicy, nie zmutowanej starej. Dokładnie dlatego ten mechanizm wraca w Lekcji 22 jako podstawa niemutowalnej aktualizacji stanu.

Kolega napisał const zaktualizowany = { ilosc: 10, ...produkt } i nie rozumie, dlaczego pole ilosc w wyniku zawsze jest takie samo jak w oryginalnym produkt, mimo że próbuje ustawić je na 10. Wyjaśnij dlaczego i popraw kod.

Lekcja 11 · Część B

== vs ===, truthy i falsy

== przed porównaniem po cichu konwertuje typy, co bywa zaskakujące ("5" == 5 daje true, mimo że jedno to tekst, a drugie liczba). === porównuje wartość i typ, bez konwersji — dlatego niemal zawsze powinieneś/aś używać === i !==.

W JS istnieje krótka lista wartości „falsy” (traktowanych jak false w warunku): false, 0, "" (pusty string), null, undefined, NaN. Wszystko inne jest „truthy”. Ma to znaczenie przy renderowaniu warunkowym — wrócimy do tego w Lekcjach 24 i 25.

Sprawdź się

Jaki wynik (true/false) da "5" === 5, a jaki "5" == 5? Dlaczego są różne?

Pokaż przykładową odpowiedź

"5" === 5 to false (różne typy: string i liczba). "5" == 5 to true, bo == najpierw konwertuje string "5" na liczbę 5, a dopiero potem porównuje.

Moduły JS: import / export

Problem, który to rozwiązuje

Twój projekt to nie jeden wielki plik — masz osobno main.jsx, App.jsx, do tego dochodzi cała biblioteka react (którą zainstalowałeś/aś przez npm, Lekcja 2). Te pliki muszą się jakoś ze sobą komunikować: main.jsx potrzebuje Twojego komponentu App, a App.jsx potrzebuje funkcji z biblioteki React. Skąd plik ma „wiedzieć”, co jest dostępne w innym pliku, a co jest jego prywatną sprawą?

Moduły JS to wbudowany w język sposób na jawne rozwiązanie tego problemu: każdy plik osobno decyduje, co udostępnia innym (export), a inne pliki osobno deklarują, co konkretnie chcą stamtąd wziąć (import). Bez tego nic z zewnątrz pliku nie jest widoczne — a to, co nie zostało wyeksportowane, jest prywatne dla tego pliku.

Eksport domyślny — Twój własny App.jsx

Zajrzyj do własnego App.jsx — na samym końcu masz export default App. To znaczy: „jeśli ktoś zaimportuje coś z tego pliku bez podawania konkretnej nazwy, dostanie właśnie to”. Plik może mieć tylko jeden taki eksport domyślny — logiczne, bo komponent zwykle ma dokładnie jedną „główną” rzecz do zaoferowania.

W main.jsx widzisz odpowiadający mu import: import App from './App.jsx'. Bez klamer — bo importujesz właśnie ten jeden, domyślny eksport. Nazwę App po lewej stronie mógłbyś nawet zmienić na dowolną inną (import CokolwiekChcesz from './App.jsx' zadziałałoby identycznie) — przy eksporcie domyślnym nazwa nie jest „zaszyta” w pliku źródłowym, ustala ją osoba importująca.

Eksport nazwany — paczka z wieloma rzeczami do wyboru

Tu jest kluczowa różnica, o którą pytałeś/aś. Paczka react to nie pojedynczy komponent jak Twój App.jsx — to cała biblioteka, oferująca wiele osobnych, niezależnych od siebie funkcji: useState, ale też useEffect, useRef, createContext, Fragment, StrictMode (dokładnie to, co widzisz owinięte wokół <App /> w Twoim main.jsx!) i sporo innych. Żaden z nich nie jest „tym jedynym głównym” — to raczej menu, z którego bierzesz dokładnie te pozycje, których akurat potrzebujesz.

Klamry to właśnie mechanizm „wybierania z menu po nazwie”. Możesz wziąć jedną rzecz:

import { useState } from 'react'

...albo od razu kilka naraz, oddzielając przecinkami — to wciąż jeden import, jedna linijka:

import { useState, useEffect } from 'react'

W przeciwieństwie do eksportu domyślnego, tu nazwa musi się zgadzać z tym, jak dana rzecz nazywa się w pakiecie źródłowym (nie możesz dowolnie nazwać jej po lewej stronie, tak jak przy App) — logiczne, skoro wybierasz konkretną pozycję z menu po jej nazwie, a nie jedyną dostępną rzecz.

Co by było, gdyby react zamiast tego miał eksport domyślny? Musiałbyś/abyś zaimportować całą bibliotekę jako jeden obiekt i sięgać do jej funkcji przez kropkę: import React from 'react', a potem React.useState(...). To zresztą dokładnie tak wyglądał starszy styl pisania Reacta, więc jeśli natkniesz się na taki kod w starszym tutorialu, będziesz już wiedział/a, dlaczego wygląda inaczej niż to, czego uczy ten kurs — to ten sam mechanizm, inaczej zapisany.

Pokaż przykładową odpowiedź

useState to jeden z wielu nazwanych eksportów paczki react — trzeba go wskazać po nazwie w klamrach, żeby JavaScript wiedział, którą dokładnie rzecz z menu chcesz. App jest jedynym eksportem domyślnym swojego pliku — domyślny eksport importuje się bez klamer, pod dowolnie wybraną nazwą.

Lekcja 13 · Część C

Czym jest komponent

Komponent funkcyjny to zwykła funkcja JavaScript, której nazwa zaczyna się wielką literą, i która zwraca opis UI zapisany w JSX. To nie jest tylko konwencja stylistyczna — React dosłownie po wielkości pierwszej litery odróżnia Twój własny komponent (<App />) od zwykłego tagu HTML (<div>, <p>).

W większych aplikacjach dzieli się interfejs na wiele mniejszych, wielokrotnego użytku komponentów. Proste, jednoekranowe aplikacje — takie jak zadanie webowe na egzaminie INF.04, gdzie wymagany jest dokładnie jeden komponent — często w całości mieszczą się w jednej takiej funkcji.

Sprawdź się

Co konkretnie poszłoby nie tak, gdybyś nazwał/a swój komponent app (małą literą) i spróbował/a użyć go jako <app />?

Pokaż przykładową odpowiedź

React potraktowałby <app /> jak zwykły, nieznany tag HTML (podobnie jak wymyślony <foo>), a nie jak wywołanie Twojej funkcji — komponent by się nie wyrenderował tak, jak zamierzałeś/aś.

Lekcja 14 · Część C

Czym jest JSX

JSX (JavaScript XML) to rozszerzenie składni JavaScript, które pozwala pisać opis struktury interfejsu w sposób przypominający HTML, bezpośrednio wewnątrz kodu JS — bez sklejania stringów, bez osobnego pliku szablonu. Konkretnie chodzi o zapis taki jak ten:

function App() {
  return (
    <h1>Cześć</h1>   // ← to jest właśnie JSX
  )
}

To, co widzisz między nawiasami po return — tekst ze znacznikami < i >, wyglądający jak HTML — to właśnie JSX. Nie jest to ani czysty JavaScript (JS sam w sobie nie ma pojęcia o znacznikach w stylu <h1>), ani czysty HTML (jest wpisany wprost w środek funkcji, nie w osobnym pliku .html) — to hybryda tych dwóch, właśnie JSX.

Kluczowe: JSX nie jest częścią samego języka JavaScript ani nie jest rozumiany przez przeglądarkę wprost. To czysta „sztuczka” na etapie budowania — narzędzie takie jak Vite (Lekcja 3) przepuszcza Twój kod przez kompilator, który zamienia każdy fragment JSX na zwykłe wywołania funkcji JavaScript, zanim kod trafi do przeglądarki. Klasyczny, najczęściej spotykany w tłumaczeniach sposób pokazania tego „pod spodem” wygląda tak:

// to piszesz (JSX):
const element = <h1 className="tytul">Cześć</h1>

// na to się kompilowało (klasyczny mechanizm JSX):
const element = React.createElement(
  "h1",
  { className: "tytul" },
  "Cześć"
)

React.createElement(typ, propsy, dzieci) tworzy zwykły obiekt JavaScript opisujący element — to właśnie z takich obiektów React buduje Virtual DOM (Lekcja 15). Ten przykład dobrze pokazuje samą ideę (JSX to skrót na wywołania funkcji, nie magia), ale jedna rzecz w nim jest dziś nieaktualna: nowoczesne narzędzia — w tym Twój projekt, zbudowany na Vite z automatycznym trybem JSX — kompilują ten sam kod do nieco innej, wewnętrznej funkcji, nie dosłownie do React.createElement. Konkretna nazwa funkcji nie ma znaczenia dla Ciebie jako programisty; ważny jest wniosek, że to zawsze zwykłe wywołanie funkcji JS, tworzące opisowy obiekt — nigdy nic, czego przeglądarka „magicznie” nie rozumie.

Masz na to namacalny dowód pod ręką: otwórz swój App.jsx i sprawdź górę pliku. Mimo że w każdym komponencie używasz JSX (całego return (...) ze znacznikami), nigdzie nie ma import React from 'react' — a mimo to wszystko działa. Gdyby JSX naprawdę kompilował się do React.createElement, ten import byłby konieczny (tak to wyglądało w starszych wersjach Reacta, sprzed ok. 2020 roku — dlatego wciąż zobaczysz go w wielu starszych tutorialach). To, że u Ciebie działa bez niego, jest właśnie dowodem, że nowoczesne narzędzie zrobiło to nieco inaczej pod spodem.

Dlaczego React w ogóle wybrał podejście „kompiluj do funkcji JS” zamiast np. szablonów tekstowych (jak w niektórych innych bibliotekach)? Bo dzięki temu masz w opisie interfejsu pełną moc języka, którego już się uczysz — zmienne, funkcje, .map(), warunki — bez uczenia się osobnej, ograniczonej „składni szablonów”.

Skoro już wiesz, czym jest JSX i jak mniej więcej działa pod spodem, przejdźmy do konkretnych zasad składniowych, o których trzeba pamiętać, pisząc go na co dzień:

  • className zamiast class — class to zarezerwowane słowo w JavaScript (do definiowania klas obiektowych), więc React użył innej nazwy.
  • htmlFor zamiast for na elemencie <label> — z tego samego powodu: for jest zarezerwowanym słowem w JavaScript (używanym w pętlach), więc przy łączeniu etykiety z polem formularza (<label htmlFor="tytul">Tytuł</label> + <input id="tytul" />) React wymaga htmlFor. Pełny, działający przykład formularza zobaczysz w Lekcji 23 — tu wystarczy zapamiętać samą nazwę i powód.
  • Każdy tag musi być zamknięty, nawet te, które w zwykłym HTML bywają „otwarte”: <img />, <br />, nie <img>.
  • Jeden korzeń — return musi zwrócić dokładnie jeden element nadrzędny obejmujący wszystko (albo Fragment, patrz Lekcja 16).
  • Osadzanie wyrażeń JS przez klamry {wyrażenie} — działa i jako wartość atrybutu (src={osoba.zdjecieUrl}), i jako treść wewnątrz taga (<p>{osoba.imie}</p>). Ważne: to musi być wyrażenie (coś, co zwraca wartość) — nie da się tak wprost wstawić instrukcji if czy pętli for (stąd w Reakcie do warunków i list używa się wyrażeń: operatora ?:, &&, oraz metody .map()).
  • camelCase w atrybutach — onClick nie onclick, onChange nie onchange. Pełna zasada dla wszystkich atrybutów — zaraz niżej.

Lekcja 15 · Część C

Virtual DOM — jak React w ogóle rysuje stronę

Prawdziwy DOM (Document Object Model) to drzewo obiektów reprezentujące stronę w przeglądarce. Jego bezpośrednia, częsta manipulacja (jak w „czystym” JS) jest kosztowna.

React utrzymuje w pamięci lekką, opisową kopię interfejsu — Virtual DOM. Gdy wywołujesz setter stanu (np. setWartosc(...)), React: (1) uruchamia ponownie funkcję komponentu, budując nowy Virtual DOM na podstawie nowych danych, (2) porównuje go z poprzednią wersją (proces zwany diffing), (3) aktualizuje w prawdziwym DOM tylko te fragmenty, które faktycznie się różnią (reconciliation) — reszta strony zostaje nietknięta.

Dzięki temu nie musisz sam pisać „znajdź ten konkretny <p> i zmień w nim tekst” — wystarczy opisać, jak ma wyglądać cały interfejs dla aktualnych danych, a React ustali różnicę sam.

Sprawdź się

Wyobraź sobie przycisk, który po kliknięciu zwiększa licznik o 1. Opisz własnymi słowami, co dzieje się krok po kroku od kliknięcia do zmiany liczby na ekranie. Użyj słów: stan, setter, Virtual DOM, re-render.

Pokaż przykładową odpowiedź

Kliknięcie wywołuje funkcję obsługi zdarzenia, która woła setter (np. setLicznik) z nową wartością. React zauważa zmianę stanu, ponownie uruchamia funkcję komponentu (re-render), budując nowy Virtual DOM na podstawie zaktualizowanych danych, porównuje go z poprzednim i aktualizuje w prawdziwej stronie tylko ten fragment (samą liczbę), który się zmienił.

Lekcja 16 · Część C

Jeden korzeń i <Fragment>

Skoro return musi zwrócić dokładnie jeden element, całą zawartość komponentu zwykle owija się w jeden <div>. Czasem jednak dodatkowy <div> przeszkadza — np. psuje układ CSS oparty o bezpośrednie dzieci elementu nadrzędnego (flexbox, grid), np. gdy kilka kart ma być ułożonych jedna obok drugiej.

Na taki wypadek istnieje Fragment — „niewidzialny” kontener, który spełnia wymóg jednego korzenia, ale sam nie tworzy żadnego elementu w prawdziwym DOM:

return (
  <>
    <h1>Tytuł</h1>
    <p>...</p>
  </>
)

Pokaż przykładową odpowiedź

Jeśli każda karta jest opakowana w dodatkowy, niepotrzebny <div>, to on staje się bezpośrednim dzieckiem zamiast właściwej zawartości, co może zaburzyć zamierzony układ — Fragment pozwala tego uniknąć, gdy owijanie jest potrzebne tylko ze względu na wymóg JSX.

Lekcja 17 · Część D

Renderowanie list przez .map() w JSX

To najważniejszy pojedynczy wzorzec w tym kursie — łączy trzy rzeczy, które już znasz osobno: metodę .map() (Lekcja 8), funkcje strzałkowe (Lekcja 6) i osadzanie wyrażeń w JSX (Lekcja 14):

const imiona = ["Ala", "Bartek", "Celina"]

return (
  <ul>
    {imiona.map((imie) => (
      <li key={imie}>{imie}</li>
    ))}
  </ul>
)

.map() zwraca tablicę elementów JSX (jeden <li> na każde imię) — a React potrafi wyrenderować tablicę elementów bezpośrednio, tak jakby to był pojedynczy element.

Ten sam wzorzec działa identycznie niezależnie od tego, w jaki tag wrapujesz elementy listy — <ul> (lista nieuporządkowana), <ol> (lista numerowana) czy zwykły <div> z blokami. Zmienia się tylko tag dookoła, sama logika .map() pozostaje taka sama.

Skoro tablica ma właściwość .length (Lekcja 8), bardzo naturalne jest pokazanie licznika elementów obok samej listy — to zwykłe osadzenie wyrażenia w JSX, nic nowego:

<h2>Liczba pozycji: {imiona.length}</h2>

Taki licznik automatycznie aktualizuje się przy każdym renderze, bo .length jest zawsze przeliczane na bieżąco z aktualnej tablicy w stanie — nie trzeba go osobno „ręcznie” aktualizować.

Lekcja 18 · Część D

Atrybut key

React potrzebuje sposobu na rozróżnienie elementów listy między kolejnymi renderami — do tego służy specjalny prop key, unikalny wśród rodzeństwa (nie musi być unikalny w całej aplikacji).

Bez stabilnego klucza React może błędnie dopasować elementy przy aktualizacji listy, co prowadzi do trudnych do znalezienia błędów (np. stan przypisany do złego elementu po zmianie kolejności). Dlatego jeśli elementy listy mają unikalne, stabilne id (np. z bazy danych), używamy właśnie jego — nigdy indeksu z .map((element, index) => ...), jeśli lista może się zmieniać (dodawanie, usuwanie, sortowanie).

Sprawdź się

Część E

Interaktywność i stan

Ostatni, najważniejszy odcinek: jak komponent „pamięta” dane i reaguje na akcje użytkownika.

Lekcja 19 · Część E

Obsługa zdarzeń

W zwykłym HTML pewnie pisałeś/aś np. onclick="mojaFunkcja()" — wygląda jak wywołanie funkcji, ale technicznie to wciąż zwykły tekst w cudzysłowie (string), tak samo jak wartość każdego innego atrybutu HTML. Przeglądarka dopiero w locie odczytuje ten tekst i wykonuje go jako kod. W React jest inaczej: atrybuty zdarzeń są zapisane camelCase i przyjmują bezpośrednio samą funkcję jako wartość, nie tekst do późniejszego odczytania: onClick={mojaFunkcja} — bez cudzysłowu, bez nawiasów wywołania, tylko nazwa funkcji wstawiona przez klamry (Lekcja 14) wprost jako wartość.

Najczęściej spotykane: onClick (kliknięcie), onChange (zmiana wartości inputa/checkboxa), onSubmit (wysłanie formularza). React opakowuje natywne zdarzenia przeglądarki we własny, spójny system (tzw. SyntheticEvent), ale w praktyce używa się tego dokładnie tak samo jak zdarzeń natywnych.

Funkcję, którą podpinasz pod zdarzenie (jak obsluz w onClick={obsluz}), często nazywa się po angielsku handlerem (dosłownie: „tym, co obsługuje”) — to tylko inna nazwa na to samo, czym już się zajmowałeś/aś: zwykłą funkcję, która ma się wykonać w reakcji na akcję użytkownika. Zobaczysz to słowo w dokumentacji i w kodzie innych osób, więc warto je znać, ale nie kryje się za nim nic nowego.

Przypomnienie z Lekcji 6 (bo to dokładnie tu ma zastosowanie): skoro taki handler to zwykła funkcja, a nie string, obowiązuje ta sama zasada co przy każdym innym przekazywaniu funkcji — onClick={obsluz} przekazuje samą funkcję, gotową do wywołania później, po kliknięciu. Dopisanie nawiasów, onClick={obsluz()}, wywołuje ją od razu, w trakcie renderowania — to wciąż ta sama pułapka, tylko teraz w kontekście konkretnych zdarzeń, których się właśnie uczysz.

Sprawdź się

Jaka jest różnica między onClick={obsluz} a onClick={obsluz()}?

Pokaż przykładową odpowiedź

onClick={obsluz} przekazuje samą funkcję — zostanie wywołana dopiero po kliknięciu. onClick={obsluz()} wywołuje obsluz od razu, w trakcie renderowania, a do onClick trafia to, co ta funkcja zwróciła (często nic albo błąd) — kliknięcie w praktyce nic już nie zrobi.

Lekcja 20 · Część E

Hook useState

Hook to specjalna funkcja Reacta (zawsze zaczyna się od use), pozwalająca „podpiąć się” pod wewnętrzne mechanizmy Reacta wewnątrz komponentu funkcyjnego. useState — pamięć stanu — to tylko jeden z wielu wbudowanych hooków, choć zdecydowanie najważniejszy i najczęściej używany.

Dlaczego kurs uczy tylko useState

Dla porządku, żebyś wiedział/a, że reszta świata Reacta istnieje: inne popularne hooki to m.in. useEffect (efekty uboczne — najczęściej pobieranie danych z serwera po załadowaniu komponentu), useRef (wartość przetrwała między renderami, ale jej zmiana nie wywołuje ponownego renderu — często dostęp bezpośrednio do elementu DOM) oraz useContext (przekazywanie danych w głąb wielu zagnieżdżonych komponentów bez ręcznego podawania ich na każdym poziomie).

Ten kurs celowo uczy wyłącznie useState — nie dlatego, że reszta jest nieważna, tylko dlatego, że dokładnie tyle wymaga zadanie webowe na egzaminie INF.04. Sprawdzone na kilku realnych arkuszach z poprzednich sesji: każdy z nich wprost wymaga dokładnie jednego komponentu, a dane są zawsze dostarczone lokalnie z góry (plik z danymi albo wpisane wprost w kodzie), nigdy pobierane z zewnętrznego serwera w trakcie działania aplikacji. To strukturalnie eliminuje powody, dla których sięga się po pozostałe hooki: nie ma efektu ubocznego do obsłużenia (stąd zbędny useEffect), nie ma czego omijać w cyklu renderowania (stąd zbędny useRef), i nie ma przez co „przebijać się” danymi, skoro komponent jest tylko jeden (stąd zbędny useContext). useState w zupełności wystarcza.

Zasada hooków: wywołujesz je zawsze na najwyższym poziomie funkcji komponentu — nigdy wewnątrz if, pętli czy zagnieżdżonej funkcji — i zawsze w tej samej kolejności przy każdym renderze. React polega na tej kolejności, żeby wiedzieć, który zapamiętany stan do którego wywołania useState należy. Zobaczmy to na pełnym, kompletnym komponencie — nie na wyrwanym z kontekstu fragmencie — żeby dokładnie było widać, gdzie to wywołanie się znajduje.

// POPRAWNIE — useState na najwyższym poziomie funkcji App,
// zaraz na początku, przed jakimkolwiek "if" czy inną logiką
import { useState } from "react"

function App() {
  const [licznik, setLicznik] = useState(0)
  // licznik    -> aktualna wartość (liczba), np. 0
  // setLicznik -> funkcja, którą wywołasz, żeby tę wartość zmienić

  return (
    <button onClick={() => setLicznik(licznik + 1)}>
      Kliknięto {licznik} razy
    </button>
  )
}

export default App

A tak wygląda złamanie tej zasady — kod, który wygląda niewinnie, ale jest błędny:

// BŁĄD — useState wewnątrz "if", nie na najwyższym poziomie
function App() {
  if (jakisWarunek) {
    const [licznik, setLicznik] = useState(0)  // ← tak nie wolno
  }

  return (
    <p>...</p>
  )
}

Problem: jeśli jakisWarunek jest raz true, a raz false (między jednym renderem a drugim), to useState czasem się wykonuje, a czasem nie — React gubi się w tej samej kolejności wywołań, o której mowa w zasadzie wyżej, i myli, który zapamiętany stan do czego należy. Stąd twarda reguła: useState zawsze na samej górze funkcji komponentu, bezwarunkowo, przy każdym bez wyjątku renderze.

Kluczowe: zwykła zmienna lokalna funkcji (let x = 0) resetowałaby się do wartości początkowej przy każdym ponownym wywołaniu funkcji komponentu (a re-render to właśnie ponowne wywołanie funkcji!). useState pamięta swoją wartość między renderami, niezależnie od tego, że sama funkcja komponentu wykonuje się od nowa. Wywołanie zwróconego settera (setLicznik(...)) zapisuje nową wartość i planuje ponowne wyrenderowanie komponentu z tą nową wartością.

Rozbijmy to na części: licznik i setLicznik

const [licznik, setLicznik] = useState(0)
  • licznik — zwykła wartość (tu: liczba), aktualny stan w danym renderze. Czytasz ją, wyświetlasz w JSX, używasz w obliczeniach — tak jak każdą inną zmienną. Nigdy jej nie przypisujesz bezpośrednio (licznik = 5), zresztą i tak byś nie mógł/mogła — to const.
  • setLicznik — funkcja, nie wartość. Jej jedyne zadanie: gdy ją wywołasz z nową wartością, każe Reactowi zapamiętać tę wartość na potrzeby następnego renderu i zaplanować przerysowanie komponentu.

Prześledźmy to klatka po klatce na przykładzie przycisku z licznikiem wyżej:

  1. Pierwszy render: useState(0) zwraca licznik = 0. Przycisk pokazuje „Kliknięto 0 razy”.
  2. Klikasz przycisk → wywołuje się () => setLicznik(licznik + 1), czyli setLicznik(1).
  3. React zapamiętuje: „przy następnym renderze tego komponentu, ten konkretny useState ma zwrócić 1, nie 0”.
  4. React ponownie wywołuje całą funkcję komponentu (re-render). Linijka const [licznik, setLicznik] = useState(0) wykonuje się od nowa — ale useState „wie”, że to nie pierwsze wywołanie, i zwraca zapamiętaną wartość: licznik = 1.
  5. Przycisk teraz pokazuje „Kliknięto 1 razy”.

Zwróć uwagę: 0 wewnątrz useState(0) ma znaczenie wyłącznie przy pierwszym renderze. Przy każdym kolejnym React ignoruje ten argument i podstawia zapamiętaną, aktualną wartość zamiast niego.

Skąd bierze się akurat nazwa setLicznik? To Twój wybór, nie wymóg Reacta — pamiętasz z Lekcji 9, że przy destrukturyzacji tablicowej liczy się wyłącznie pozycja, nie nazwa? To dotyczy też useState: const [a, b] = useState(0) zadziałałoby dokładnie tak samo — a byłoby wartością, b funkcją do jej zmiany — tylko byłoby dużo mniej czytelne. Nazwa setLicznik to po prostu przyjęta w całym środowisku React konwencja: przedrostek set + nazwa stanu, zaczynająca się wielką literą. Trzymanie się jej nie jest obowiązkowe, ale sprawia, że Twój kod (i kod innych osób) od razu jest czytelny — widać na pierwszy rzut oka, do czego dana funkcja służy.

Lekcja 21 · Część E

Domknięcia (closures)

Po co mi to, skoro nic tu sam/a nie piszę?

Uczciwie: ta lekcja nie nauczy Cię nowej składni ani nowej komendy, którą od teraz będziesz świadomie wpisywać. Domknięcia (closures) to mechanizm, który działa automatycznie, w tle, za każdym razem, gdy definiujesz funkcję wewnątrz komponentu — a robiłeś/aś to już wielokrotnie w tym kursie (każdy handler zdarzenia, np. onClick={() => ...}).

Więc po co to poznawać? Bo bez tego jedna rzecz w Twoim własnym kodzie wygląda jak niewytłumaczalna magia: skąd funkcja obsługująca kliknięcie „wie”, jaka jest aktualna wartość stanu, skoro nigdy jej tej wartości nie przekazujesz jako argumentu? Ta lekcja odpowiada dokładnie na to pytanie — i dzięki temu, zamiast wkuwać wzorzec na pamięć, będziesz rozumiał/a, dlaczego on w ogóle działa.

Definicja i przykład

Domknięcie to ogólna cecha JavaScriptu (nie coś specyficznego dla Reacta): funkcja „pamięta” zmienne ze swojego otoczenia (scope), w którym została zdefiniowana — nawet gdy jest wywoływana później, z zupełnie innego miejsca. Zobaczmy to na konkretnym, kompletnym przykładzie:

function App() {
  const [licznik, setLicznik] = useState(0)

  function zwiekszLicznik() {
    setLicznik(licznik + 1)
    // ↑ używa "licznik" i "setLicznik", mimo że żadne z nich
    //   nie jest parametrem funkcji zwiekszLicznik!
  }

  return <button onClick={zwiekszLicznik}>Kliknięto {licznik} razy</button>
}

zwiekszLicznik jest zdefiniowana wewnątrz App — dzięki temu automatycznie ma dostęp do wszystkiego, co jest lokalne dla App, w tym licznik i setLicznik, bez potrzeby przekazywania ich jako argumentów. To dokładnie ten sam mechanizm, którego (być może nieświadomie) używałeś/aś już wielokrotnie, pisząc własne handlery zdarzeń w swojej aplikacji.

Dlaczego to działa poprawnie przy każdym kliknięciu

Połączmy to z tym, co już wiesz z Lekcji 15 i 20: re-render to ponowne wywołanie całej funkcji komponentu. Za każdym razem, gdy App wykonuje się od nowa, definiowana jest w niej zupełnie nowa wersja zwiekszLicznik — i ta nowa wersja domyka („zamyka w sobie”) akurat tę aktualną wartość licznik z tego konkretnego renderu:

// Render 1: licznik = 0
//   → powstaje wersja zwiekszLicznik, domykająca licznik = 0
// klik → setLicznik(0 + 1) → React planuje re-render

// Render 2: licznik = 1
//   → poprzednia wersja zwiekszLicznik jest wyrzucana
//   → powstaje NOWA wersja, domykająca już licznik = 1

Dzięki temu nigdy nie musisz się martwić o to, że przycisk „pamięta” starą, nieaktualną wartość — każdy render dostaje własną, świeżą wersję funkcji, domkniętą wokół danych dokładnie z tego renderu.

Własnymi słowami: dlaczego funkcja zdefiniowana wewnątrz komponentu „widzi” zmienną stanu tego komponentu, chociaż ta nie jest jej parametrem?

Pokaż przykładową odpowiedź

Bo ta funkcja jest zdefiniowana wewnątrz funkcji komponentu, a funkcje w JavaScript automatycznie mają dostęp do zmiennych zdefiniowanych w otaczającym je zasięgu (scope) — nie trzeba ich jawnie przekazywać jako argumenty, tak jak nie musisz przekazywać zmiennej lokalnej do funkcji zagnieżdżonej wewnątrz tej samej funkcji w zwykłym JS.

Pokaż przykładową odpowiedź

Cztery razy w sumie: raz przy pierwszym renderze (domyka licznik = 0), a potem po każdym z trzech kliknięć — kolejno domykając licznik = 1, licznik = 2, licznik = 3. Każdy re-render to nowe wywołanie App, a więc i nowa wersja funkcji zdefiniowanej w jej środku.

Lekcja 22 · Część E

Niemutowalność stanu

Najważniejsza zasada praktyczna w Reakcie: nigdy nie modyfikuj bezpośrednio (nie mutuj) wartości przechowywanej w stanie. Zawsze twórz nową wartość i przekazuj ją do settera. Z Lekcji 10 pamiętasz już fakt: .push() mutuje tablicę, spread (...) tworzy nową. Ta lekcja tłumaczy, dlaczego ta różnica ma w Reakcie realne, praktyczne znaczenie — nie tylko czysto teoretyczne.

Analogia: zeszyt na półce

Wyobraź sobie półkę z podpisanymi zeszytami. React, żeby sprawdzić, czy coś się zmieniło, nie otwiera zeszytu i nie czyta zawartości — patrzy tylko na to, czy to fizycznie ten sam zeszyt, czy inny (innymi słowy: czy referencja w pamięci jest ta sama, czy inna). Jeśli dopiszesz coś długopisem do zeszytu, który już stoi na półce (mutacja) — to z zewnątrz wciąż wygląda jak ten sam zeszyt, bo nim jest. React przejdzie obok, nie zauważy różnicy, mimo że zawartość w środku faktycznie się zmieniła. Jeśli zamiast tego położysz na półce nowy zeszyt (nową tablicę/obiekt ze spreadem), zastępując nim stary — React od razu widzi: „to nie jest ten sam zeszyt co wcześniej”, i reaguje.

To samo w kodzie

// BŁĄD: mutacja "w miejscu" — ten sam zeszyt, dopisana treść
elementy[0].wartosc++
setElementy(elementy)
// referencja "elementy" się NIE zmieniła — to wciąż ten sam obiekt w pamięci
// React "widzi" tę samą referencję co poprzednio i nie przerysowuje widoku,
// mimo że console.log(elementy) pokazałby już poprawną, zmienioną wartość!

To jeden z najczęstszych błędów początkujących: „w konsoli dane się zmieniły, ale ekran nic nie pokazuje”. Poprawny wzorzec — nowy zeszyt zamiast dopisywania do starego, tu na przykładzie aktualizacji jednego elementu tablicy obiektów po jego id:

// OK: nowa tablica (.map), a w niej nowy obiekt tylko dla zmienianego elementu
setElementy(
  elementy.map((element) => {
    if (element.id === id) {
      return { ...element, wartosc: element.wartosc + 1 }
    } else {
      return element
    }
  })
)

.map() zawsze zwraca nową tablicę (nowy zeszyt na półce — React to wykryje), spread {...element, wartosc: ...} tworzy nowy obiekt tylko dla zmienianego elementu. Pozostałe obiekty w tablicy są zwracane bez zmian — i to jest w porządku, bo one się faktycznie nie zmieniły, więc mogą zostać tym samym „zeszytem”, co poprzednio.

Dodawanie nowego elementu do tablicy w stanie

Aktualizacja to tylko jedna z trzech podstawowych operacji na tablicy w stanie. Druga: dopisanie zupełnie nowego elementu — np. nowego zgłoszenia z formularza. Wzorzec ze spreadem z Lekcji 10 ([...tablica, nowyElement]), zastosowany na tablicy obiektów i połączony z setterem:

function dodajElement(nowyObiekt) {
  setElementy([...elementy, nowyObiekt])
}

...elementy kopiuje wszystkie dotychczasowe obiekty do nowej tablicy (nowy „zeszyt”, ale z tą samą zawartością), a nowyObiekt na końcu dopisuje się jako dodatkowy element. Nowy obiekt zwykle budujesz z aktualnych wartości stanu formularza — np. { id: nastepneId, tytul: wpisanyTytul, wykonane: false } — a nie ma znaczenia, że sam ten obiekt jest tworzony „od zera” literałem { }, a nie spreadem: spread potrzebny jest tu do skopiowania tablicy, nie do budowy nowego elementu.

Usuwanie elementu z tablicy w stanie

Trzecia operacja: usunięcie elementu po jego id. Tu nie używasz spreadu — sięgasz po .filter() z Lekcji 8, które (jak pamiętasz) samo z siebie zwraca nową tablicę, więc niemutowalność masz „za darmo”:

function usunElement(id) {
  setElementy(elementy.filter((element) => element.id !== id))
}

.filter() przepuszcza do nowej tablicy wszystkie elementy poza tym, którego id pasuje do usuwanego — czyli zostaje dokładnie to, co miało zostać. Zwróć uwagę na !==, nie ===: warunek mówi „zostaw ten element”, więc musi być prawdziwy dla wszystkich oprócz usuwanego.

Lekcja 23 · Część E

Komponenty kontrolowane (controlled inputs)

Zwykły input HTML „sam pamięta” swoją wartość wewnątrz przeglądarki. W React preferuje się oddanie tej wartości pod pełną kontrolę stanu — stąd „controlled input”: to, co widać na ekranie, zawsze pochodzi ze stanu, a nie z pamięci samej przeglądarki. Poniżej pełne wzorce dla czterech najczęściej spotykanych pól formularza.

Checkbox / switch

const [zaznaczony, setZaznaczony] = useState(true)

<input
  type="checkbox"
  checked={zaznaczony}
  onChange={() => setZaznaczony(!zaznaczony)}
/>

checked zawsze pochodzi ze stanu, onChange aktualizuje ten stan w reakcji na działanie użytkownika. !zaznaczony to negacja logiczna — „ustaw wartość przeciwną do obecnej”. Powstaje w ten sposób pętla jednokierunkowego przepływu danych: stan → wygląd na ekranie → akcja użytkownika → nowy stan → nowy wygląd. Ta sama pętla powtarza się we wszystkich poniższych wariantach.

Pole tekstowe

const [imie, setImie] = useState("")

<input
  type="text"
  value={imie}
  onChange={(e) => setImie(e.target.value)}
/>

Zamiast checked pole tekstowe używa propa value. e to obiekt zdarzenia (przekazywany automatycznie do każdej funkcji obsługującej onChange), a e.target to sam element <input>, który wywołał zdarzenie — stąd e.target.value odczytuje aktualnie wpisany tekst, dokładnie w momencie, gdy użytkownik coś wpisał.

Częsty błąd początkujących: ustawienie samego value={imie} bez onChange. Pole wygląda wtedy na „zablokowane” — można kliknąć, ale nic nie da się wpisać. Powód: stan nigdy się nie zmienia (nie ma kto go zaktualizować), więc value zawsze wraca do tej samej wartości przy każdym renderze. Zasada: value i onChange na inpucie zawsze idą w parze.

Pole liczbowe — pułapka z typem

const [wiek, setWiek] = useState(0)

<input
  type="number"
  value={wiek}
  onChange={(e) => setWiek(Number(e.target.value))}
/>

Kluczowa pułapka: mimo że type="number" ogranicza, co użytkownik może wpisać, e.target.value zawsze zwraca tekst (string) — nigdy liczbę — niezależnie od typu inputa. Jeśli zapiszesz tę wartość w stanie bez konwersji, dostaniesz np. wiek równe "25" (string), a nie 25 (liczba). Wygląda tak samo na ekranie, ale zachowuje się inaczej w obliczeniach i porównaniach: "25" + 1 da "251" (sklejenie tekstu), nie 26. Dlatego zawsze jawnie konwertujesz: Number(e.target.value) (albo parseInt(e.target.value, 10) dla liczb całkowitych).

Lista rozwijalna — <select>

To jedna z nielicznych sytuacji, gdzie React różni się składniowo od zwykłego HTML w sposób, który łatwo przeoczyć. W czystym HTML zaznaczoną opcję wskazuje atrybut selected na konkretnym <option>. W React tak się nie robi — zamiast tego value ustawiasz na samym <select>, dokładnie tak jak przy zwykłym tekstowym incie:

const [kategoria, setKategoria] = useState("")

<select value={kategoria} onChange={(e) => setKategoria(e.target.value)}>
  <option value="">-- wybierz --</option>
  <option value="1">Komedia</option>
  <option value="2">Obyczajowy</option>
  <option value="3">Sensacyjny</option>
</select>

<select> „wie”, którą opcję pokazać jako zaznaczoną, porównując swój value z wartością value każdego <option> — dopasowany <option> zostaje wybrany automatycznie, bez dotykania go osobno. onChange na <select> działa identycznie jak na inpucie: e.target.value zwraca value aktualnie wybranej opcji (jako string — jeśli reprezentuje liczbę, jak tu kategorię 1–3, też będzie wymagać Number(...), zanim użyjesz jej do porównań liczbowych).

Pokaż przykładową odpowiedź

Jedna wspólna zmienna boolean mogłaby przechowywać tylko jeden stan „wszystko włączone / wszystko wyłączone” naraz, więc nie dałoby się odwzorować dowolnej kombinacji.

Lekcja 24 · Część E

Wyszukiwanie w danych i obsługa braku wyniku

Bardzo częsty wzorzec: użytkownik podaje jakąś wartość (np. numer, kod, nazwę), aplikacja szuka pasującego elementu w tablicy danych i pokazuje albo wynik, albo czytelny komunikat, że nic nie znaleziono. Ta lekcja łączy kilka rzeczy, które już znasz — .find() z Dodatku, warunki i wartości truthy/falsy z Lekcji 11, kontrolowany input liczbowy z poprzedniej lekcji — w jeden, kompletny wzorzec.

Przypomnienie: .find()

.find(funkcja) przechodzi przez tablicę i zwraca pierwszy element, dla którego funkcja zwróciła true. Jeśli żaden element nie pasuje, zwraca specjalną wartość undefined — nie null, nie pustą tablicę, nie błąd.

const produkty = [
  { kod: 101, nazwa: "Zeszyt" },
  { kod: 102, nazwa: "Długopis" },
  { kod: 103, nazwa: "Linijka" },
]

const wynik = produkty.find((p) => p.kod === 999)
// wynik === undefined, bo żaden produkt nie ma kodu 999

Sprawdzenie, czy coś znaleziono

Skoro brak wyniku to undefined, a undefined jest wartością „falsy” (Lekcja 11), można to sprawdzić wprost, bez porównywania jawnie do undefined:

if (wynik) {
  // wynik istnieje — jest tu prawdziwym obiektem produktu
} else {
  // wynik to undefined — nic nie znaleziono
}

Renderowanie warunkowe w JSX: ?: i &&

Skoro w JSX nie da się wstawić instrukcji if wprost (Lekcja 14), do wyboru jednego z dwóch wariantów UI używa się operatora trójargumentowego warunek ? coś : cośInnego — dokładnie tak samo, jak już go użyłeś/aś w Lekcji 6 (zadanie z pogodą):

<p>
  {wynik ? wynik.nazwa : "Nie znaleziono produktu o takim kodzie."}
</p>

Gdy chcesz pokazać coś tylko czasem, a w przeciwnym razie nie pokazywać zupełnie nic (żadnego tekstu zastępczego), używa się krótszego operatora &&:

<p>
  {wynik && "Znaleziono: " + wynik.nazwa}
</p>

Działa to, bo && w JavaScript zwraca swój lewy operand, jeśli jest „falsy” (tu: undefined, gdy nic nie znaleziono — React wtedy po prostu nic nie wyrenderuje), a w przeciwnym razie zwraca swój prawy operand (tu: gotowy tekst z nazwą produktu).

Pełny przykład: input liczbowy + wyszukiwanie + wynik

Łącząc to wszystko z kontrolowanym polem liczbowym z Lekcji 23 — łącznie z konwersją Number(...), bez której porównanie p.kod === wpisanyKod nigdy by się nie powiodło (string nie jest ściśle równy liczbie, Lekcja 11):

const [kod, setKod] = useState(0)
const [znaleziony, setZnaleziony] = useState(null)

function szukaj() {
  const produkt = produkty.find((p) => p.kod === kod)
  setZnaleziony(produkt)
  // tak samo można od razu wypisać wynik do konsoli, jeśli zadanie tego wymaga:
  console.log(produkt ? produkt.nazwa : "Nie znaleziono produktu o takim kodzie.")
}

return (
  <>
    <input type="number" value={kod} onChange={(e) => setKod(Number(e.target.value))} />
    <button onClick={szukaj}>Szukaj</button>
    <p>{znaleziony ? znaleziony.nazwa : "Nie znaleziono produktu o takim kodzie."}</p>
  </>
)

Zwróć uwagę na onClick={szukaj} — bez dodatkowej strzałki, bo tu akurat chcemy przekazać samą funkcję (bez argumentów) bezpośrednio, dokładnie ten przypadek z Lekcji 6, gdzie funkcja ma się wykonać dopiero po kliknięciu, a nie od razu.

Pokaż przykładową odpowiedź

Pokaż przykładową odpowiedź

Pokaż przykładową odpowiedź

Porównanie === sprawdza też typ (Lekcja 11), więc "101" === 101 to zawsze false — .find() nigdy nie znajdzie dopasowania, mimo że wartości „wyglądają” tak samo. Poprawka: konwersja Number(e.target.value) przy zapisie do stanu.

Lekcja 25 · Część E

Renderowanie warunkowe

W Lekcji 24 poznałeś/aś ?: i && przy okazji wyszukiwania — ale to ogólny wzorzec, przydatny wszędzie tam, gdzie interfejs ma wyglądać inaczej w zależności od stanu, nie tylko przy szukaniu w danych: pokazanie komunikatu o błędzie, podświetlenie wybranego elementu, ukrycie przycisku, gdy coś jeszcze się ładuje. Zbierzmy to w jednym miejscu i dodajmy dwa wzorce, których jeszcze nie znasz.

Przypomnienie: ?: i &&

Operator ?: wybiera jedną z dwóch wartości do wyrenderowania:

<p>{godzina < 18 ? "Dzień dobry" : "Dobry wieczór"}</p>

Operator && pokazuje coś tylko wtedy, gdy warunek jest prawdziwy — w przeciwnym razie nie renderuje nic:

{bladWalidacji && <p className="blad">{bladWalidacji}</p>}

Oba działają, bo zwracają wartość — a klamry w JSX (Lekcja 14) przyjmują dokładnie wartości, nie instrukcje.

Pułapka: && z liczbą po lewej stronie

Bardzo częsty przypadek: chcesz wyrenderować listę tylko wtedy, gdy tablica nie jest pusta. Intuicyjnie kusi, żeby napisać po prostu {dane.length && (...)} — w końcu .length równe 0 jest „falsy”, prawda? To pułapka:

// BŁĄD: gdy dane.length wynosi 0, na ekranie pojawi się... cyfra 0!
{dane.length && (
  <ul>{dane.map((el) => <li key={el.id}>{el.urzadzenie}</li>)}</ul>
)}

&& nie zwraca true/false — zwraca dokładnie tę wartość, która zdecydowała o wyniku. Gdy dane.length to 0, całe wyrażenie zwraca liczbę 0, nie false. A React renderuje liczby (w przeciwieństwie do false, null czy undefined, które nic nie pokazują) — więc zamiast pustego miejsca zobaczysz samotną cyfrę „0” na stronie.

Lekarstwo: zawsze porównuj jawnie, żeby po lewej stronie && był prawdziwy boolean, nie liczba:

// OK — dane.length > 0 zawsze zwraca true albo false, nigdy liczbę
{dane.length > 0 && (
  <ul>{dane.map((el) => <li key={el.id}>{el.urzadzenie}</li>)}</ul>
)}

if przed return — całkiem inny widok

?: i && dobrze sprawdzają się, gdy różnica dotyczy fragmentu JSX. Czasem jednak dwa warianty są na tyle różne (albo obszerne), że wygodniej jest zdecydować o całym widoku, zanim w ogóle zaczniesz go budować — używając zwykłego if, ale przed return, nie w środku niego:

function App() {
  const [zaladowano, setZaladowano] = useState(false)

  if (!zaladowano) {
    return <p>Wczytywanie danych...</p>
  }

  return (
    <div>
      <h1>Dane są gotowe</h1>
      {/* reszta interfejsu */}
    </div>
  )
}

To wciąż zwykły JavaScript — funkcja komponentu to zwykła funkcja, a if na jej najwyższym poziomie działa dokładnie tak, jak się spodziewasz: gdy warunek jest prawdziwy, funkcja kończy działanie na tym return i reszta kodu (drugi return) w ogóle się nie wykonuje. W przeciwieństwie do ?:/&&, tu obie strony mogą być dowolnie duże i skomplikowane, bo to nie jest wyrażenie osadzone w klamrach — to zwykłe rozgałęzienie funkcji.

if dla samego fragmentu — zmienna z JSX

Wzorzec z poprzedniego punktu działa, gdy cały widok komponentu ma być inny. Co jednak, gdy warunkowy ma być tylko fragment — np. lista — a reszta interfejsu (nagłówek, formularz) ma się wyświetlić zawsze? Wtedy nie da się zrobić dwóch osobnych return. Rozwiązanie: przygotuj fragment JSX w zmiennej przez if/else przed głównym return, a potem osadź tę zmienną przez klamry w odpowiednim miejscu:

let listaHtml

if (dane.length > 0) {
  listaHtml = (
    <ul>
      {dane.map((el) => <li key={el.id}>{el.nazwa}</li>)}
    </ul>
  )
} else {
  listaHtml = <p>Brak danych</p>
}

return (
  <div>
    <h1>Nagłówek</h1>
    {listaHtml}
  </div>
)

Uwaga na szczegół: listaHtml musi być zadeklarowana przez let, nie const — bo wartość przypisujesz jej dopiero wewnątrz if/else (Lekcja 5). Mechanika jest identyczna jak w poprzednim punkcie — to wciąż zwykły JavaScript, tylko wynik trafia do zmiennej zamiast bezpośrednio do return.

Warunkowa klasa CSS

Bardzo częsty przypadek: chcesz nadać elementowi inną klasę CSS w zależności od stanu — np. podświetlić wybraną kartę. Skoro className to zwykły atrybut przyjmujący string (Lekcja 14), a ?: to zwykłe wyrażenie zwracające jedną z dwóch wartości, można je po prostu połączyć:

<div className={jestWybrany ? "karta karta-wybrana" : "karta"}>
  {produkt.nazwa}
</div>

Gdy jestWybrany jest true, element dostaje obie klasy (karta karta-wybrana), a Ty w CSS definiujesz dodatkowy wygląd dla .karta-wybrana — bez pisania osobnego, zduplikowanego bloku JSX tylko po to, żeby zmienić jedną klasę.

Sprawdź się — zadanie 1

Mając zmienną liczbaWynikow, napisz wyrażenie JSX wyświetlające „Znaleziono wyniki” gdy jest większa od zera, a w przeciwnym razie nic (żadnego tekstu zastępczego).

Pokaż przykładową odpowiedź

Sprawdź się — zadanie 2

Masz komponent, który na początku funkcji sprawdza const [uzytkownik, setUzytkownik] = useState(null). Napisz if przed głównym return, który — gdy uzytkownik jest null — zwróci od razu <p>Musisz się zalogować</p>, zanim funkcja dojdzie do reszty kodu.

Pokaż przykładową odpowiedź

Sprawdź się — zadanie 3

Mając zmienną stanu ulubione (boolean) i stały ciąg klasy "gwiazdka", napisz atrybut className, który dodatkowo dokleja klasę "zaznaczona", gdy ulubione jest true.

Pokaż przykładową odpowiedź

Sprawdź się — zadanie 4

Komponent renderuje nagłówek i formularz zawsze, a pod nimi listę zadania — ale tylko gdy tablica nie jest pusta, w przeciwnym razie tekst „Brak zadań”. Dlaczego nie da się tego zrobić przez proste „if przed return” z dwoma osobnymi return, i jaki wzorzec zamiast tego zastosujesz?

Pokaż przykładową odpowiedź

„If przed return” z dwoma return nadaje się tylko wtedy, gdy cały widok ma być inny — tu jednak nagłówek i formularz muszą wyświetlić się zawsze, niezależnie od warunku, więc nie można wcześniej „wyjść” z funkcji. Trzeba przygotować fragment JSX (listę albo komunikat) w zmiennej zadeklarowanej przez let, ustawić ją w if/else przed głównym return, a potem osadzić tę zmienną przez klamry { } w odpowiednim miejscu wewnątrz stałego JSX.

  • Nazewnictwo — znaczące nazwy zmiennych i funkcji (elementy, zwiekszLicznik, pokazAktywne), nie a, x1, tmp. Polskie czy angielskie nazwy — dowolnie, byle konsekwentnie w całym pliku.

Warto wyrobić sobie ten nawyk już teraz, na małych przykładach — w każdym kolejnym, większym projekcie (w tym w projektach ocenianych, gdzie czytelność kodu bywa wprost punktowanym kryterium) zwraca się on wielokrotnie.

Lekcja 27 · Część G

Instalacja i użycie biblioteki zewnętrznej (na przykładzie Bootstrapa)

Arkusz egzaminacyjny wprost wymaga użycia biblioteki Bootstrap do stylowania (przełączniki, przyciski). To dobra okazja, żeby poznać ogólny, uniwersalny wzorzec dodawania dowolnej gotowej biblioteki do już istniejącego projektu — nie tylko Bootstrapa.

Krok 1: instalacja

Z Lekcji 2 pamiętasz, że zależności projektu (dependencies w package.json) instaluje się poleceniem npm install. Tam widziałeś/aś to na przykładzie react i react-dom, zainstalowanych automatycznie przy tworzeniu projektu przez Vite. Dokładnie tym samym poleceniem dodajesz nową bibliotekę do już istniejącego projektu, w dowolnym momencie:

npm install bootstrap

To polecenie: pobiera pliki biblioteki do node_modules, i dopisuje bootstrap jako nową pozycję w dependencies Twojego package.json — możesz to sprawdzić, otwierając ten plik po instalacji.

Krok 2: import stylów z zainstalowanej paczki

Z Lekcji 4 znasz już mechanizm importowania CSS bezpośrednio w pliku JS (import './index.css') — to specjalna sztuczka, którą rozumie Vite. Dokładnie ten sam mechanizm działa dla CSS pochodzącego z zainstalowanej paczki — różnica jest tylko w ścieżce: zamiast ./ (plik lokalny, Twój własny) podajesz samą nazwę paczki, a po niej ścieżkę do konkretnego pliku CSS wewnątrz niej:

import 'bootstrap/dist/css/bootstrap.css'

Tę linijkę dodajesz raz, w main.jsx (albo w App.jsx — działa w obu miejscach, tak samo jak własny CSS) — od tego momentu wszystkie klasy Bootstrapa są dostępne do użycia w całej aplikacji, wystarczy nadać je przez className (Lekcja 14).

Skąd wiedzieć, jakich klas użyć

Nie musisz znać na pamięć wszystkich klas Bootstrapa — na egzaminie arkusz zawsze dołącza tabelę z gotowymi przykładami markupu dla wymaganych elementów (przełączniki, przyciski). Twoje zadanie to przepisać ten przykład na JSX (pamiętaj: class → className, Lekcja 14), a nie wymyślać klasy samodzielnie od zera.

Częsty problem na Windowsie: PowerShell blokuje npm

Na wielu stanowiskach z Windowsem (w tym część szkolnych pracowni) domyślna polityka bezpieczeństwa PowerShell blokuje uruchamianie skryptów — a npm na Windowsie jest technicznie skryptem .ps1. Efekt: próba npm install (albo nawet npm run dev) kończy się błędem w stylu:

File ...\npm.ps1 cannot be loaded because running scripts is disabled on this system.

To nie ma nic wspólnego z Twoim kodem ani z Reactem — to ustawienie systemowe. Dwa sposoby naprawy:

  • Trwałe rozwiązanie (nie wymaga uprawnień administratora): Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned, potwierdzone Y. Od tej pory npm działa normalnie przy każdym kolejnym projekcie.
  • Szybkie obejście, jednorazowo: wywołaj bezpośrednio wrapper .cmd zamiast .ps1: npm.cmd install bootstrap.

Warto zapamiętać ten komunikat błędu — jeśli go zobaczysz na stanowisku egzaminacyjnym, wiesz już, że to nie błąd w Twoim podejściu do zadania, tylko ustawienie systemu, które da się szybko obejść.
